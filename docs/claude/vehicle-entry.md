# Vehicle entry (step 1), vehicle types, owners, delete, data checks

Project documentation for Claude Code and Codex. Moved here unchanged from `CLAUDE.md` on 2026-11-16 to keep that file short; `CLAUDE.md` holds the index. Update this file when the feature changes.

- Dashboard and five registration categories exist in the prototype.

- Customer database UI supports create, list, and detail views.

- New vehicle registration has eight steps, all implemented (entry, transfer notice, inspection, submit documents, receipt, plate, book, Delivery); the sections below describe each.

- Vehicle entry supports Single entry and validated Batch import from `.xlsx` and UTF-8 `.csv`.

- Customer, brand, and finance-company choices come from the database (`/api/finance-companies`, added like brands with a "+ เพิ่มไฟแนนซ์" form; no seed data).

- `ประเภทรถ` is a dropdown with 14 unique user-specified choices. `รย.17-จักรยานยนต์สาธารณะ` (user 2026-10-08, migration `20261008230000_vehicle_type_ry17`) counts as a motorcycle everywhere: one rule `isMotorcycleType` / `motorcycleTypeWhere` in `backend/src/vehicles/vehicle-reference-data.ts` (copied as `isMotorcycleBody` in `frontend/src/lib/vehicle-kind.ts`) = body starting `รย.12-` or `รย.17-`; never test `startsWith('รย.12-')` directly again. It uses the motorcycle fee set, the motorcycle tax rate and `STAFF_MOTO` scope; its ตัดบัญชี / แจ้งย้าย / Bangkok inspection rows are copies of `รย.12-น้อยกว่า 300cc` (Claude's choice, the user only gave the Samut Prakan inspection rate: 300, against 200 for รย.12).

- Vehicle entry records the owner type (`บุคคลธรรมดา` / `นิติบุคคล`, required) and an optional finance company. Financed vehicles are stored as a `VehicleOwner` with the finance company as the juristic registered owner and the chosen type as `hirerType`; the submit-documents page (Step 4) shows this automatically and only asks for the owner type on older vehicles that have none. See `frontend/src/lib/vehicle-owner.ts` and `VehiclesService.ownerDataFor`.

- Deleting a vehicle (added 2026-09-23): soft delete only. `DELETE /api/vehicles/:id` needs a `remark` (mandatory reason)
  and is `ADMIN`-only, as are `GET /api/vehicles/deleted` and `POST /api/vehicles/:id/restore`. `Vehicle.deletedAt` /
  `deletedReason` / `deletedById` hold the current state; every delete and restore also writes a `VehicleEditLog` row so
  repeated cycles stay auditable. `VehicleEditLog.editedById` (added 2026-09-24) records who made each edit, delete, restore or inspection correction (null for rows before then and for scripts). Deleted vehicles are filtered out of every list, queue, search and the customer portal
  (`deletedAt: null` in each `where`). A vehicle cannot be deleted once it has any `DocumentSubmission` (including FAILED),
  any `InvoiceLine`, or is linked as the new vehicle of a `PlateSwap` - fix it with แก้ไข instead. `Vehicle.chassis` is no
  longer `@unique` in Prisma: uniqueness is a Postgres partial unique index `Vehicle_chassis_active_key` over
  `chassis WHERE "deletedAt" IS NULL`, so a deleted chassis can be keyed in again (never use `findUnique({ where: { chassis } })`).
  UI: ลบ button per row plus a "รายการที่ลบแล้ว" panel with กู้คืน, both ADMIN-only, in `/registration/new-vehicle/entry`.

- Saved-vehicle list on `/registration/new-vehicle/entry` (added 2026-09-25): `GET /api/vehicles` returns
  `{ vehicles, hasMore }`, 100 at a time newest-first (`offset` for "โหลดเพิ่มอีก 100 คัน", `limit` up to 1,000 so a
  reload after edit/delete keeps what is open). `q` searches the whole database (chassis, engine, plate incl.
  "4กข 4444", customer name/company, owner/hirer name); `from` / `to` (YYYY-MM-DD, inclusive) filter `Vehicle.date`.
  The date boxes are DD/MM/YYYY and accept a Buddhist year. The search/date matching lives in
  `backend/src/vehicles/vehicle-list-filter.ts`, shared with the vehicle search page below.

- Owner names at vehicle entry: without finance the form requires `ชื่อผู้ถือกรรมสิทธิ์` (stored in `VehicleOwner.name`); with finance the registered owner is the finance company name (read-only) and the form requires `ชื่อผู้ครอบครอง` (stored in `VehicleOwner.hirerName`).

- Size checks against wrong CC (user 2026-10-13, no migration; a clerk keyed a Zontes 149.5cc as `รย.12-300-799cc`, and a wrong CC changes the tax and fees): (1) at entry, `motorcycleCcMismatch` in `backend/src/vehicles/vehicle-validation.ts` (copied in `frontend/src/lib/vehicle-validation.ts`) is a blocking row error when a motorcycle's CC is outside the range of its body (`<300`, `300-799`, `800-999`, `1000+`; `รย.17` has no range), for single entry, batch import and edit. Not built: a table of known models (brand + engine-number prefix -> CC) to warn when a CC differs from earlier vehicles of the same model. (2) At the receipt step, when the receipt amount differs from the Bill, `GET /api/vehicles/document-submission/:id/size-hint?amount=` -> `{ hints[] }` (`receipt-size-hint.ts`, read access like the other document-submission GETs) retries the Bill with other values and says which one gives the receipt's amount: `{ field: 'cc' | 'weight', current, from, to }` for cars (tax scan: CC 1-10,000 step 1, weight step 5) or `{ field: 'body', suggested }`; empty = nothing matches. `ReceiptCheckPage` shows it under the "ไม่ตรง Bill" badge. It only suggests, never edits the vehicle. Motorcycle Bill fees do not depend on the CC bracket (flat tax), so a motorcycle's wrong bracket is caught by (1), not by the receipt.

- Wrong-data warnings at vehicle entry + daily report (user 2026-10-13, no migration; an audit found 10 wrong brands, 5 CC / body mismatches and 2 chassis numbers of 16 / 18 characters, most keyed on 30/09-01/10): rules in `backend/src/vehicles/vehicle-data-check.ts` (chassis part copied in `frontend/src/lib/vehicle-data-check.ts`). They are **warnings, never errors** (user's choice: warn, tick, confirm), unlike the motorcycle CC range above which blocks. (1) Chassis: not 17 characters (`CHASSIS_LENGTH`) or containing I / O / Q or a symbol (`CHASSIS_CHARS`). (2) Known model: vehicles in the system whose chassis starts with the same 8 characters should share brand, CC and body (`MODEL_BRAND` / `MODEL_CC` / `MODEL_BODY`). Nothing to maintain: `buildKnownModels` learns from saved vehicles and trusts a field only when at least 3 vehicles agree and they are at least 80% of that prefix (`MODEL_MIN_VEHICLES`, `MODEL_MIN_SHARE`, Claude's numbers), so one wrong first entry or a model with real variants (pickup with / without canopy) does not produce warnings. Contract: `POST /api/vehicles` answers 409 `{ needsConfirm: true, warnings: [{ row, chassis, warnings: [{ code, message, short, key }] }] }` and saves nothing until resent with `confirmedWarnings` = every `key` shown (a changed warning has a new key); each confirmed vehicle gets a `VehicleEditLog` row "ยืนยันข้ามคำเตือนตอนคีย์: ..." with the user. `PATCH /api/vehicles/:id` returns them as `dataWarnings` in its existing 409 next to `affected` (only warnings **caused by this edit**, so an old vehicle with a 16-character chassis can still have its colour fixed) and takes `confirmedWarnings` with `confirm`; the remark in the log gets "ยืนยันข้ามคำเตือนตอนแก้: ...". `GET /api/vehicles/known-model?chassis=&excludeId=` -> `{ model: { prefix, count, brand { id, name } | null, cc | null, body | null } | null, warnings }` feeds the entry form: `components/VehicleDataCheck.tsx` shows a "16/17 หลัก" counter beside the chassis label, a "รุ่นนี้เคยคีย์ N คัน: Zontes · 149.5 · รย.12-..." row with a "ใช้ค่านี้" button that fills brand / CC / body, and the confirm box with the "ตรวจกับเอกสารแล้ว" tick (single entry, batch import where the warnings also appear in the preview table after the first save click, and the edit dialog through `EditImpactWarning`). Daily report: overview alert `data-suspect` (medium, `docs` list, `OverviewService.suspectVehicles` + `findSuspectVehicles`) lists vehicles **not yet invoiced or closed** with any of the warnings above, a motorcycle CC outside its body range, or no owner row; each row opens that vehicle's edit form (`/registration/new-vehicle/entry?focus=<chassis>&edit=1`), and the LINE secretary cards pick it up through the alerts. It reads every active vehicle on each overview load. Duplicate receipt numbers are deliberately not reported: 36 numbers are shared by 2-3 vehicles on production, each read from its own receipt photo (the DLT numbers per counter), so they are not mistakes. Not built: a confirm step for dates that are not today (the most frequent correction, 157 edits in 30 days), trimming double spaces in owner names. Not tested in a browser (no dev login available to Claude).
