# LINE bots: personal secretary, customer bot, statement and Yamaha mail

Project documentation for Claude Code and Codex. Moved here unchanged from `CLAUDE.md` on 2026-11-16 to keep that file short; `CLAUDE.md` holds the index. Update this file when the feature changes.

- Personal secretary on LINE (เลขาส่วนตัว, user 2026-10-07, migration `20261007200000_secretary_notes`, code in `backend/src/secretary/`, backend only, no web page): a LINE Official Account bot talks to the owner's personal LINE only (env `LINE_CHANNEL_ACCESS_TOKEN`, `LINE_USER_ID`, `LINE_CHANNEL_SECRET`, see `.env.example`; never commit or paste them in chat). Push: `SecretaryService.sendMorning` / `sendEvening` build Flex cards from `OverviewService.overview()` (no AI, no tokens); morning = overdue bills, stuck vehicles, yesterday's spend, customers past due, top alerts; evening = today's spend, problems (high alerts), what each step did, staff activity, tomorrow's reminders. Staff names come from where the system records who did it: vehicle entry, submit and receipt-received (author columns since 2026-10-08), VehicleEditLog / AuditLog editors and DeliverySlip.createdBy; plate / book received and the other jobs have no author yet. Amounts are exact, not rounded. Cards list everything (user 2026-10-08 "ข้อมูลควรครบก่อน", replacing the earlier 3-5 line limits): every problem, every step done, every staff member, every overdue customer and reminder; `SECTION_MAX` (15 lines per section, `card-parts.ts`) only keeps the bubble under LINE's 30 KB, and whatever exceeds it follows as text messages (`overflowTexts`), so `buildMorningMessage` / `buildEveningMessage` return `LineMessage[]`. Cards link to web pages when `FRONTEND_ORIGIN` is a real URL (`urlFor` in `card-parts.ts`; alert `href`s come from the overview). The overview now also returns `workingCapital.overdue` { count, amount, customers[{ customerName, count, amount, maxDaysOver }] } = invoices past `Invoice.dueDate` (`overdueByCustomer`). Chat (plan A, keyword commands, user's choice): LINE posts to `POST /api/secretary/webhook` (PUBLIC in `access-policy.ts`, every other `/api/secretary` route ADMIN), which first checks `X-Line-Signature` against the raw body (`NestFactory.create(..., { rawBody: true })`, `line-webhook.ts`; 401 without a valid signature, 503 if `LINE_CHANNEL_SECRET` is unset), answers LINE at once and replies in the background (reply token, falling back to push); only events from `LINE_USER_ID` are answered. Commands (`commands.ts`, `replies.ts`): สรุปเช้า, สรุปเย็น, ค้างจ่าย, รถติดขัด, ยอดใช้จ่าย, คำสั่ง (help), plus quick-reply buttons. Note vault (`SecretaryNote`, `notes.ts`, `NotesService`): `จำ <ชื่อ> = <ข้อความ>` (same name overwrites and returns the old value), `ขอ <ชื่อ>` (exact, else contains), `ลืม <ชื่อ>` (exact only, returns the deleted value), `ตู้เอกสาร` (list); max 200 notes, no passwords or ID numbers. Manual sends: `npm run secretary:test | secretary:morning | secretary:evening` in `backend/`. Schedule (user 2026-10-07: morning 09:00, evening 16:00 Thai time): `.github/workflows/secretary.yml` calls `POST /api/secretary/run?slot=morning|evening` (PUBLIC in `access-policy.ts`, guarded by header `x-secretary-key` = env `SECRETARY_RUN_KEY` >= 16 chars, 503 when unset, 401 when wrong; `run-key.ts`), because the Render free plan sleeps and an in-process cron would miss. The same slot on the same Thai day sends once (in-memory guard against retries, `runScheduled`). GitHub only runs schedules from the default branch (master), so nothing fires from dev; the workflow needs repo secrets `SECRETARY_BACKEND_URL` and `SECRETARY_RUN_KEY`, and the manual "Run workflow" button only exists once the file is on master. Finance card (user 2026-10-31 "ส่งผ่านเลขาส่วนตัว", no migration, `finance-pending.ts` reads, `finance-message.ts` builds): "การเงินค้าง" is pushed as its own push right after the morning card (separate request because LINE takes at most 5 messages per push and a long morning card already has follow-up texts), and is returned for the command "การเงิน" / "การเงินค้าง" (quick-reply button added; `finance` is matched before `overdue` because the text contains ค้าง; "สรุปเช้า" in chat returns the morning card only). Lines only when non-zero, each linking to its page: payroll (previous month's run DRAFT / APPROVED, and the current month from day 20 when not PAID; a month with no run at all is only flagged for the current month), waiting for billing (same rules as the billing queue: delivered vehicles not in a live invoice and not closed + delivered other jobs not billed or closed; every customer listed, past `SECTION_MAX` in a follow-up text), receivables (every ISSUED invoice, company / personal split, oldest), 50 ทวิ pending (`WHT_PENDING_WHERE`, over 30 days / within 5 days of it), quotations (approved not billed / applied, expired, waiting, drafts), and on days 1-15 a reminder for last month's accounting package + ภ.พ.30 (the system cannot know it was sent). Thresholds (day 20, 5 days, 1-15) are Claude's choices. Previewed read-only against production data; not sent to LINE from here. Free-text questions with AI (plan B), file/photo vault and a Rich Menu are not built. Weekly reminders (user 2026-10-31 "ตั้งเตือนกันลืม", no migration, `backend/src/secretary/reminders.ts`): a fixed table `WEEKLY_REMINDERS` (weekday + Bangkok time + text + page link): Monday 16:00 วางบิล Lexus, Tuesday 16:00 เช็คยอด SPI ก่อนส่งงานวันพุธ, Wednesday 15:00 วางบิล Spac EV + MC Superbike, Friday 15:00 วางบิล T Double E. `POST /api/secretary/run?slot=reminder` sends every reminder of today whose time has passed and was not sent yet (one in-memory mark per reminder per day, so a retry or the daily evening run never double-sends); `secretary.yml` has cron lines `0 9 * * 1,2` and `0 8 * * 3,5` for it (a new reminder needs a row in the table and a cron line). Command "ตารางเตือน" (quick-reply button) lists the table; `npm run secretary:reminder` sends by hand. Not sent to LINE from here (today was a Saturday: nothing due).

- Customer LINE bot (บอทไลน์ลูกค้า, user 2026-10-09, no migration, code in `backend/src/customer-line/`, backend only): a second LINE Official Account for customers ("Jitkusol Auto"), separate from the personal secretary account and with its own keys (env `LINE_CUSTOMER_CHANNEL_SECRET`, `LINE_CUSTOMER_CHANNEL_ACCESS_TOKEN`, see `.env.example`). `POST /api/customer-line/webhook` (PUBLIC in `access-policy.ts`, every other `/api/customer-line` route ADMIN) checks `X-Line-Signature` like the secretary webhook (401 without a valid signature, 503 when the secret is unset), answers LINE at once and replies in the background. It answers anyone who writes, so it never reads or writes vehicle or customer data and never shows the office's prices (the tax check below shows government tax only). Only feature so far (user's choice: chat bot, ตรอ. check only): a text containing "ตรอ" (spaces and dots ignored) gets two quick-reply buttons รถยนต์ / มอเตอร์ไซค์, each a LINE `datetimepicker` (postback data `tro:car` / `tro:moto`, max = today in Bangkok); the picked registration date comes back in the same postback, so no conversation state is kept, and the bot answers whether a ตรอ. inspection is needed, with the date from which it is (shown in พ.ศ.). The rule is read from `requiresInspection` of the tax renewal calculator (cars 7 years, motorcycles 5, date-to-date, due on the anniversary itself), plus a fixed note that tax overdue by more than a year always needs one. Since the menu below was added the bot answers every text message, so the auto-response messages of LINE Manager must be switched off (both would answer). The date can also be typed in the same message, Buddhist year accepted ("ตรอ รถยนต์ 15/03/2562", day/month/year with / - or ., a 2-digit year = พ.ศ. 25xx; `parseTypedTro`): with a vehicle word the bot answers for that kind, without one it answers for both kinds, and a bad or future date gets a format hint. The date picker only works in the LINE phone app. Bottom menu + button cards (user 2026-10-09 "แถบเมนูด้านล่างพร้อมการ์ดปุ่มกด", no migration): the document lists that were 13 keyword auto-responses in LINE Manager now live in `customer-menu.ts` (`MENU_CARDS`: welcome, documents, new registration + 4 cases, transfer, plate swap, colour change, tax renewal, plate copy, ตรวจนอก, forms with the 6 Drive links, staff contact = a call button to `CONTACT_PHONE`, the delivery slip's number, confirmed by the user) and are sent as Flex cards whose buttons send a keyword back as a normal message (or open a link / `tel:`), so no state is kept and typing the keyword gives the same card. `findMenuCard`: exact keyword first, else the longest keyword contained in the sentence (keywords under 4 characters only match exactly); a text that matches nothing and a `follow` event get the welcome card; images, stickers and unknown postbacks get no answer; ตรอ. is checked before the menu. If LINE refuses a card the same content is sent as plain text. Rich Menu (`rich-menu.ts`, image `rich-menu.png` 2500x1686 drawn from `rich-menu.html` with headless Chrome, copied to `dist` through `assets` in `nest-cli.json`): 9 areas (จดใหม่, โอนรถ, สลับเลข, เปลี่ยนสี, ต่อภาษี, คัดป้าย / แบบฟอร์ม, เช็ก, ติดต่อเจ้าหน้าที่), each a message action; `syncRichMenu` runs on boot when the access token is set, creates the menu named `jitkusol-main-<RICH_MENU_VERSION>`, uploads the image, sets it as the default for all users and deletes its own older versions (bump the version to change the image or areas; nothing happens when the current one is already the default). Claude's choices, not confirmed: the menu layout and artwork, answering unknown texts with the welcome card (it will get in the way if staff chat is ever switched on in LINE Manager). Tax check (user 2026-10-09 "ใส่ฟีเจอร์เช็คค่าภาษี ... อย่าลืมรถไฟฟ้า ... นิติด้วย ... ให้ใช้ง่ายที่สุด", `tax-check.ts`, no migration): "เช็กภาษี" / "ค่าภาษี..." / a text starting with "ภาษี" opens a card of vehicle kinds (`car` = รย.1 by CC incl. hybrids and 4-door pickups, `ev` = รย.1 BEV by weight, `pickup` = รย.3 by weight, `moto`, `emoto`), then the bot asks one thing at a time: CC or weight (typed number), owner บุคคลธรรมดา / นิติบุคคล (only `car` and `ev`, where a juristic owner doubles the tax; a financed car with an individual hirer is told to pick บุคคลธรรมดา), registration date (typed in พ.ศ. or picked), and "ภาษีขาดต่อหรือยัง": one tap "ยังไม่ขาด" (the due date is then taken as the next anniversary of the registration date, `nextAnniversary`) or the expiry date when it has lapsed. The answer is a card with the yearly tax (age discount shown), late surcharge, each overdue year when several are owed, the total payable to the DLT and the ตรอ. result. The amounts come from `calculateVehicleTax` of the tax renewal job with the rate tables from `TaxService.loadRuleSet()` (cached 10 minutes), as an individual-owner / juristic calculation with no finance exemption; it shows government tax only, never the office's prices, and reads no vehicle or customer data. Unfinished answers are kept per LINE user in memory (`TaxSession`, 20 minutes, max 2,000, lost on restart); while one is open a typed text is the answer to the current question unless it is ยกเลิก, a ตรอ. question, an exact menu keyword (a Rich Menu tap) or a new tax question. `routeEvent` in `customer-line.service.ts` holds this order and is what the tests cover. A kind with no rate row (today `emoto`: `GovernmentTaxMotorcycleFlat` has no BEV row, and an electric pickup is not asked about at all) is refused at the first step with "ติดต่อเจ้าหน้าที่". The Rich Menu tile and the card `check` offer both checks. Not tested against LINE itself (unit tests + a read-only run of the calculator against the dev rate tables; the keys exist on production only).

- Statement -> tax invoice from LINE (user 2026-11-16 "ผมชอบลืมออกใบกำกับ", no migration, `backend/src/secretary/`): the owner shares the K BIZ statement CSV (`recent_transaction_*.csv`: header row `Transaction Date`, `Transaction`, `Withdrawal (Baht)`, `Deposit (Baht)`, `Account/PromptPay or Biller`, `Channel`; no payer name) into the secretary chat. `handleEvents` now also takes `message.type = file` and `postback` events (owner only, redeliveries skipped). `bank-statement.ts` (pure): `parseKbizCsv` -> deposits, `matchDeposit` against ISSUED / PAID invoices of the last 12 months by amount only: the bill's net, or the gross less WHT 0 / 1 / 3 / 5 % of ค่าบริการ, a deposit may be up to 10 baht short (transfer fee, `FEE_TOLERANCE`) or 0.5 over, 2-4 ISSUED bills of one customer may add up, bills issued after the deposit date are ignored; a PAID bill with `paidDate` = the deposit date and a fitting amount = already done. `statement-message.ts` builds the reply: a summary text (to do / already recorded / no bill found) plus a carousel with one card per deposit to act on (max 12 per carousel, warning colour when several bills fit) and one button per bill: "ใบกำกับ IVxxxx" for a COMPANY + VAT bill without a live TV, else "รับเงิน IVxxxx" (personal-account bills, and bills whose TV was issued before payment such as YM). Postback data `st|tv|tvgo|pay|paygo|<invoiceId>|<deposit date>|<wht>`; every action is two taps: `tv` / `pay` answer a confirm card (next TV number, date = deposit date, WHT amount and method from `Customer.billingWhtMethod`, missing buyer data or series not enabled = no confirm button, a warning when the date is before the latest TV), `tvgo` calls `TaxInvoiceService.issue` (`paidDate` = deposit date, `backdateConfirmed: true`) and `paygo` calls `BillingService.markPaid`; nothing is ever issued without the second tap, and the service's own checks (status, date order, lock) still apply, so a double tap answers the conflict text. `BillingModule` exports `BillingService` + `TaxInvoiceService` for this; these calls run outside a request, so `createdById` / `paidById` are null. Invoice download links (user 2026-11-16 "ลองส่งใบวางบิลที่ออกล่าสุดสองอันมาหน่อยทางไลน์"): the owner types "บิลล่าสุด" (2 newest non-VOID bills by `createdAt`; "บิลล่าสุด 5", max 5) or "บิล IV2026-155" (by number, max 5) -> `parseInvoiceLinkCommand` in `invoice-link.ts`, checked before the notes commands (the whole message must match, so "ขอ ที่อยู่" still goes to notes) -> `StatementService.invoiceLinks` (read-only) -> one plain-text message per bill with `<FRONTEND_ORIGIN>/iv?token=…&download=1&openExternalBrowser=1`. Token = same HMAC link as the tax invoice but kind `iv` (signed id prefixed `iv:`), so a tax-invoice link cannot open a bill and the reverse; 7 days. `GET /api/secretary/invoice?token=` (PUBLIC in `access-policy.ts`, 401 before any query) returns `{ invoice }` in the `/api/billing/invoices/:id` shape; page `/iv` (in `OPEN_PATHS`, no shell) shows the bill with ปริ้น / บันทึกเป็น PDF and auto-downloads `<IV no.> <customer>.pdf` when `download=1`. The link shows prices to anyone holding it, which is why only the owner can ask for it. PDF download link (user 2026-11-16 "ส่งเป็นลิ้งดาวโหลดมาเลย"; LINE bots cannot send files): the issued card's first button "ดาวน์โหลด PDF" and a second plain-text message (easy to forward to staff) carry the same `/tv` link + `&download=1&openExternalBrowser=1` (`pdfDownloadUrl`); `/tv` then builds the PDF in the browser once on load, the buttons stay as a fallback; `openExternalBrowser=1` makes LINE use the device browser because its in-app browser cannot save files. Print link: after issuing, the card has "เปิดใบกำกับ" -> `<FRONTEND_ORIGIN>/tv?token=` (needs `FRONTEND_ORIGIN` and `AUTH_SECRET`; token = base64url(id.expiry) + HMAC-SHA256, 7 days, `print-link.ts`). `GET /api/secretary/tax-invoice?token=` (PUBLIC in `access-policy.ts`, 401 before any query when the token is bad or expired) returns that one tax invoice; the page `/tv` (`OPEN_PATHS` / `isOpenPath` in `frontend/src/lib/auth.ts`: no login, no AppShell menu, proxy passes it whether logged in or not) shows it with ปริ้น and บันทึกเป็น PDF, always as ต้นฉบับ + สำเนา while the link is valid (Claude's choice: the link is how the original reaches the staff who print it; the in-app rule "original only on the issue day" is unchanged). Unit-tested (`bank-statement.spec.ts`), dry-run read-only against production bills with the user's real CSV (5 deposits all matched correctly), `/tv` browser-checked on dev with a real token and a bad one. **Not tested against LINE itself** (file download, postback buttons, the issue tap). Not built: reminders in the morning card (no statement sent for 3 days / issued but not printed), sending to staff directly (the owner forwards the link from their personal LINE), reading the bank / Yamaha emails of the work mailbox, the monthly purchase-tax PDF (user asked to be reminded after this).

- Yamaha payment notice -> tax invoice before payment (user 2026-11-16 "ให้ bot อ่านเมลยามาฮ่าเอง", no migration, `backend/src/secretary/yamaha-mail.ts` + `mail-message.ts` + `mail.service.ts`): Thai Yamaha's finance department (`finance@yamaha-motor.co.th`, subject contains `แจ้งรายละเอียด Invoice`, sometimes prefixed `Revised`) mails 2-5 days ahead: `วันที่โอนเงิน : DD/MM/YYYY`, `ยอดเงินที่โอน : n บาท`, and the bill numbers between `Invoice ดังนี้` and `กรุณาแจ้งวิธี…` (`IV2026-131` or `IV : IV2026-085`). A Gmail filter in the work mailbox forwards 5 senders to the owner's personal Gmail (label `บัญชี-bot`, skip inbox); the Google Apps Script `backend/scripts/gmail-yamaha-forwarder.gs` (installed by hand in that Gmail, `BACKEND_URL` + `SECRETARY_KEY` in Script Properties, every 15 minutes, labels sent threads `bot-sent`, never deletes or replies) posts new ones to `POST /api/secretary/mail` `{ messages: [{ id, from, subject, body }] }` -> `{ results: [{ id, status: sent | nothing-to-do | duplicate | ignored | unreadable }] }` (PUBLIC in `access-policy.ts`, guarded by header `x-secretary-key` = `SECRETARY_RUN_KEY` like `run`: 503 unset, 401 wrong; max 20 mails, body cut at 20,000 chars, message ids remembered in memory against retries). Only mails whose From address is exactly the finance address and whose subject is the notice (not `RE:` / `FW:`) are read (`isYamahaNotice`); text below a quoted `From:` is dropped. The bot pushes one card to the owner: pay date, amount, each bill with its state (`open` / `has-tv` / `paid` / `not-found` / `unusable`), a warning when the mail amount differs from the bills' net total by more than 0.5, when a bill is unknown, or when the notice is a revision, the reminder that Yamaha wants a reply and a scan sent to `pranom@…`, and a button "ใบกำกับ IVxxxx" per open bill whose customer has `billingTaxInvoiceBeforePayment`. Nothing is pushed when every bill already has a TV or is paid; a notice that cannot be parsed pushes a plain text asking the owner to open the mail. The button is postback `st|tvb|<invoiceId>|<pay date>|<bill wht>` -> confirm card -> `st|tvbgo` = `TaxInvoiceService.issue` with `beforePayment: true` (date = the pay date, may be in the future within the service's 31 days; the bill stays ISSUED; money is recorded later with "รับเงิน IV…" from the statement cards). An email is outside data: it only ever fills a card, and a forged mail can at most show a card whose two taps still issue the system's own bill. Unit-tested (`yamaha-mail.spec.ts`) and dry-run read-only against production bills (IV2026-131 paid -> no card; IV2026-153 / 154 open -> card with one button each). **Not tested**: the Apps Script, the endpoint over HTTP, LINE delivery. Not built: reading the SMBC / K-Cash Connect / e-WHT mails, drafting the reply to Yamaha, a reminder when the pay date passes without money.

- Yamaha PO / Delivery Order mail -> LINE alert (user 2026-11-16 "PO มา / DO มา ... สำคัญมากที่อยากให้เตือนเพราะต้องออกใบวางบิล", no migration, `backend/src/secretary/yamaha-po-mail.ts`, handled in `MailService.handlePurchasing` before the payment notice): the same `POST /api/secretary/mail` now also reads two mails of Yamaha's purchasing system, and the Apps Script searches three senders (`SENDERS`). PO: From exactly `accounting.info@yamaha-motor.co.th`, subject contains `purchase order (PO)` (not `RE:` / `FW:`), body line `หมายเลข po : AC693788, AC693767` (1-10 numbers, only from that line). Each PO is looked up (`loadPoStatuses`, `poNumber` contains, case-insensitive): `billed` = a non-VOID `Invoice.poNumber` has it, `approved` = an APPROVED `Quotation.poNumber` has it but no live bill, `new` = neither. The card "ยามาฮ่าส่ง PO มาแล้ว" lists every PO with its state, the count still to bill, for a `new` PO the quotations waiting for approval (`loadWaitingQuotations`: ISSUED with `yamahaMonth` set or a customer with `billingRequiresQuotation`, max 8 shown; a warning when there is none), the steps (approve the quotation with the PO number, then "ออกใบวางบิลจากใบนี้") and a button to `/accounting/quotations` when `FRONTEND_ORIGIN` is set. Nothing is pushed when every PO already has a live bill (`nothing-to-do`). DO: From exactly `purchasing@yamaha-motor.co.th`, subject `Received | Cancelled | Rejected Delivery Order: DO-YYYYMMDD-nnn` (the login notification of the same sender is `ignored`); the card shows the DO number, `Purchase Order No.`, `Invoice No.` and `Reason of …` from the body: green "ยามาฮ่ารับ DO แล้ว" (wait for the finance notice) or red for a cancelled / rejected one (issue a new DO in PR-Online, otherwise the bill is not paid). An unreadable PO / DO mail pushes a plain text asking the owner to open it. Alert only: nothing is written to the database and no button issues anything (Claude's choice: the PO number is still typed in the quotation's approve form by hand; the DO card is sent for every Received mail). Mail setup still needed by hand: the work-mailbox filter forwards `accounting.info@` but not `purchasing@` (add it, or install the script in the work mailbox itself), and the script must be (re)pasted. Unit-tested (`yamaha-po-mail.spec.ts`, bodies copied from the real mails of 2026-11-04 and 2026-11-10); production data checked read-only (AC693767 / AC693788 are both billed as IV2026-153 / 154 -> no card). **Not tested**: `getPlainBody()` output of the real mails in Apps Script, the endpoint over HTTP, LINE delivery.
