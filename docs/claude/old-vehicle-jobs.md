# Old-vehicle jobs hub (งานรถเก่า)

Project documentation for Claude Code and Codex. Update this file when the feature changes.

User decisions of 2026-11-18. The hub covers สลับเลข, งานโอน (3 types), ต่อภาษี, ยกเลิกการใช้รถ, ย้ายออก, คัดแผ่นป้าย. Not งานแจ้งย้ายยามาฮ่า, not new registration.

## Flow the user asked for

รับงาน -> เลือกประเภทงาน -> ตรวจรถ (only when needed) -> ยื่น -> รับใบเสร็จ / ป้าย / เล่ม -> ส่งงาน. "เสร็จ" = ส่งงาน (DL slip) done; billing is not part of the status. The old code had ยื่น before ตรวจรถ for transfers; the user said the real order is inspection first.

Built in rounds. **Round 1 (this file) = hub page + intake + inspection before submit + ติดขัด flag.** The submit step and everything after it still happen on each job's existing pages; the hub links there.

Not built yet (agreed, later rounds): submit / receipt forms inside the hub (side panel), pulling vehicle data into the old submit forms, removing the four old menus, making intake mandatory (old menus can still create a job directly), ค่าอากรโอน on every transfer type filled by receipt OCR, ขส. tax of the three unverified licence types read from the receipt, a brand-vs-vehicle-type warning.

## Tables (migration `20261118150000_old_vehicle_jobs`, additive)

- `OldVehicle`: one row per old vehicle, keyed once and reused by every job. `vehicleType` (the 14 รย. types + 4 ขส. types; null on backfilled rows), `vehicleClass` CAR | MOTO (from `vehicleType` via `isMotorcycleType`), plate หมวด + เลข, `chassis`, `chassisKey` (unique: upper case, no spaces / dashes / dots), `engine` (optional), `brand`, `ownerName`. Never deleted; edits need a remark and go to `AuditLog` entity `OldVehicle`.
- `OldVehicleJob`: one intake. `vehicleId`, `customerId` (job owner), `receivedDate`, `receivedIsBackfill`, `jobType` (null = รอทำ) one of `PLATE_SWAP | TRANSFER_OWNER | TRANSFER_INSPECTION | TRANSFER_MOVE_IN | TAX_RENEWAL | USE_CANCEL | MOVE_OUT | PLATE_COPY`, `jobId` (id of the real job row once submitted, no FK; unique with `jobType`), `note`, `duplicateReason`, `firstRegistrationDate` + `taxExpiryDate` (tax renewal only), inspection columns (`inspectionRequired`, `inspectionSentType` OUTSIDE | BRING_IN, `inspectionSentDate`, `inspectionCost`, `inspectionResult` PASS | FAIL, `inspectionResultDate`), ติดขัด columns (`blockedAt`, `blockedReason`, `blockedNote`, `blockedById`), soft cancel. The received date belongs to the job, not the vehicle: one row per vehicle on the hub, several jobs under it.

## Rules (`backend/src/old-vehicle-jobs/old-vehicle-job-rules.ts`, labels copied in `frontend/src/lib/old-vehicle-jobs-api.ts`)

- Inspection is decided by the system (`inspectionRequiredFor`): โอนตรวจรถ and โอนย้ายเข้า always; ต่อภาษี for ขส. types always, cars at 7 full years, motorcycles (รย.12 / รย.17) at 5, tax overdue more than 1 year, using `requiresInspection` of the tax calculator (age counted to the tax expiry date, or today when already past it); every other job never.
- Inspection cost: ส่งตรวจนอก = typed per vehicle (0 allowed), ขส. pre-filled 1,000 and editable (`defaultInspectionCost`); นำรถมาตรวจ = 0. Kept in `OldVehicleJob.inspectionCost`, not added to any Bill / No Bill total.
- Status of a job not yet submitted (`intakeStatus`): NEW (รอทำ) -> TO_INSPECT (รอส่งตรวจ; also after a FAIL) -> TO_RESULT -> TO_SUBMIT. Submitted jobs read the real job row (`linkedStatus`): TO_INSPECT / TO_RESULT (transfers filed the old way), TO_PAY (tax renewal without `paymentDate`), TO_RECEIPT, TO_PLATE (plate copy; plate swap that bought a plate), TO_BOOK (plate swap), TO_DELIVER, DONE, CANCELLED (the real job was cancelled on its own page).
- Duplicate rule: same vehicle + a different job type, or the same type whose earlier job is closed, is accepted silently; same type while an earlier one is still open = 409 `needsDuplicateReason` until `duplicateReason` is sent.
- Plate swap kind at intake (user 2026-11-18, migration `20261118160000_old_vehicle_job_swap_pair` = `OldVehicleJob.jobVariant` + `pairId`, additive): `PLATE_SWAP` needs `swapKind` `OLD_NEW` (รถเก่า กับ รถใหม่, one vehicle) or `OLD_OLD` (รถเก่า กับ รถเก่า). The user said the two old vehicles always arrive together from the same customer but may have different owner names, so `OLD_OLD` is accepted only from `POST /intake` with exactly two vehicles carrying the same `pairKey` (any string; the server issues a shared `pairId`), same customer by construction, each with its own `ownerName`, both CAR or both MOTO. `PATCH /jobs/:id/type` refuses `OLD_OLD` and refuses any change on a paired job; cancelling one intake of a pair cancels both (refused when the partner was already submitted); a vehicle with an unsubmitted paired job cannot switch CAR <-> MOTO. `HubJob.variant` carries the kind before submit (after submit it comes from `PlateSwap.kind`) and `HubJob.pair = { vehicleId, plate }` is the other vehicle. Backfilled plate swaps copy `kind` and `PlateSwap.pairId`, so pairs keyed before the hub also show as pairs. The form: choosing รถเก่า กับ รถเก่า on a vehicle adds a locked "คันคู่สลับเลข" row right after it; the `+` in a grid cell and the job dialog offer only รถเก่า กับ รถใหม่. `nextStepHref` sends the pair to `old-old/submit`.
- New vehicle of an รถเก่า กับ รถใหม่ swap (user 2026-11-18, migration `20261118170000_old_vehicle_job_new_vehicle` = `OldVehicleJob.newVehicleId`, additive, no FK): optional, chosen at intake or later from the job dialog (`newVehicleId` in `POST /intake` and `PATCH /jobs/:id/type`; empty clears it). The server only checks that the `Vehicle` exists, is not deleted and has the same class as the old vehicle, and refuses it on any other job type; the real link rules (already submitted, linked to another swap) stay in the plate-swap service at submit. `HubJob.newVehicle = { id, chassis, brandName, plate }` is the chosen vehicle before submit and `PlateSwap.newVehicleId` after. The picker (`NewVehiclePicker`) searches with the existing `GET /api/plate-swaps/vehicle-search` and shows that endpoint's `linkBlockedReason` (those rows cannot be picked). When nothing is found it links to `/registration/new-vehicle/entry` in a new tab so the half-filled intake form survives (user: "ทำหน้าลิ้งไปให้กรอกรถใหม่เลย"; the same person keys both), or tells roles that cannot write step 1 to ask the data-entry staff. The old submit page is not pre-filled yet (round 2).
- ขส. vehicles can only take ต่อภาษี. โอนย้ายเข้า is motorcycles only for now (the old submit form refuses cars).
- ติดขัด: any open job, reason from `BLOCK_REASONS` (list proposed by Claude, the user has not edited it) + free text, `OTHER` needs the text. It does not change the step. Block / unblock are written to `AuditLog` entity `OldVehicleJob`. More than `BLOCKED_ALERT_DAYS` = 3 calendar days raises the overview alert `old-job-blocked` (medium, counts every non-cancelled intake with the flag, including one whose real job finished without the flag being cleared).
- Chassis guards: stored upper case without spaces; `chassisWarnings` warns (never blocks) on a 17-character VIN containing I / O / Q or failing the ISO 3779 check digit; the lookup also reports a plate that exists with another chassis. Received date: not in the future (400); a weekend shows the usual warning on the form.

## API `/api/old-vehicle-jobs` (access: GET = ADMIN / STAFF_CAR / STAFF_MOTO / ACCOUNTANT, writes = ADMIN / STAFF_CAR / STAFF_MOTO; the service checks the vehicle's own class, read scope filters the list)

- `GET ?scope=open|done|all|inspection&q=&vehicleClass=` -> `{ vehicles: HubVehicle[], truncated }` (500 vehicles max, newest received first; `q` = plate / chassis / owner / customer). Job-type and status filters are client side.
- `GET /lookup?chassis=&plateCategory=&plateNumber=` -> `{ vehicle, plateMatches, warnings }`.
- `POST /intake { customerId, receivedDate, vehicles: [{ vehicleId? | vehicleType, plateCategory, plateNumber, chassis, engine?, brand, ownerName, jobType?, firstRegistrationDate?, taxExpiryDate?, note?, duplicateReason? }] }` (1 to 50 vehicles, one transaction; a chassis that already exists reuses that vehicle and ignores the typed vehicle data).
- `PATCH /vehicles/:id { ..., remark, expectedUpdatedAt }` (409 when stale or when the chassis matches another vehicle; CAR <-> MOTO refused once a job was submitted; vehicle type locked while an unsubmitted job has been sent to inspection; changing the type re-decides `inspectionRequired` of unsubmitted jobs). Vehicle data inside already submitted jobs is their own snapshot and is not changed.
- `PATCH /jobs/:id/type { jobType, firstRegistrationDate?, taxExpiryDate?, duplicateReason? }` until the job is sent to inspection or submitted.
- `POST /inspection-sent { sentDate, sentType, items: [{ id, cost }] }` (many vehicles at once; allowed again only after a FAIL, which is audited as `inspection-resend`), `PATCH /jobs/:id/inspection-result { result, resultDate }`, `POST /jobs/:id/inspection-undo { remark }` (clears the result, or the sent step when there is no result).
- `POST /jobs/:id/block { reason, note? }`, `POST /jobs/:id/unblock`, `POST /jobs/:id/cancel { remark }` (only before submit).

## Linking to the real jobs (`OldVehicleJobsService.sync`, idempotent)

No existing job service was changed to know about intakes. `sync` runs on every hub load and, through the app-wide `OldVehicleJobLinkInterceptor`, right after a successful create `POST` on `/api/plate-swaps` (and `/pair`), `/api/vehicle-transfers`, `/api/tax-renewals`, `/api/vehicle-use-cancellations`, `/api/vehicle-move-outs`, `/api/plate-copies`, before the response is sent (the create response itself is the row before the copy; the pages reload their list). A failed link is only logged and never fails the filing; the next hub load retries. It finds real job rows (not cancelled) without an `OldVehicleJob`:

1. If the vehicle (same `chassisKey`) has an unsubmitted intake created before the job, the job is linked to it (`jobId`, and `jobType` is set to the real job's type). Candidates in order: same job type, then any transfer type for a transfer (received as one kind, filed as another), then an intake still at รอทำ. A PASS inspection done before submit is copied to the job so its own flow does not ask again: `VehicleTransfer` inspection columns (only when still empty), `TaxRenewal.inspectionConfirmed`, or `TaxRenewal.inspectionDate` for ขส.; audited as `inspection-from-intake`.
2. Otherwise the vehicle and an intake row are created from the job (`receivedIsBackfill = true`, received date = the Bangkok date the job was keyed). This is how jobs keyed before the hub existed appear on it (user approved 2026-11-18).

Because inspection can now precede the submit date, two transfer rules were relaxed in `vehicle-transfer.service.ts`: "วันที่ยื่นต้องไม่หลังวันที่ส่งตรวจ" applies only to jobs filed the old way (`inspectedBeforeSubmit` = a linked `OldVehicleJob` with a PASS result exists; not inferred from dates, since inspection and filing can be the same day), and the return date floor, in both `markReturned` and `update`, is the later of the submit date and the inspection result date.

Volumes: the list reads at most 5,000 vehicles (most recently touched first; an intake touches the vehicle's `updatedAt`), decides open / done in memory because the status of a submitted job lives in its own table, and returns 500; `truncated` is true when either cap is hit. `scope=inspection` filters in SQL (unsubmitted jobs with `inspectionRequired`) and is what the inspection page uses. Production had about 30 old-vehicle jobs on 2026-11-18, so a persisted status column was left for a later round.

Reviewed on 2026-11-18 by an independent reviewer (no critical findings; the important ones above were fixed). Still open from that review: job mutations do not send an `expected...` value from the dialog (the server only guards its own read-then-write), one intake form cannot take two jobs for the same vehicle, a re-filed job after its real job was cancelled gets a backfilled row instead of reusing the intake, the plate-swap submit link always goes to `old-new`, the hub's "overdue more than 1 year" test (`days / 365`) can differ from the tax calculator (`lateMonths / 12`) by a day.

Known gap of round 1: the ขส. tax-renewal No Bill still adds the fixed 1,000 inspection fee of `tax-renewal-fee.ts`; an amount edited on the hub is stored on the intake only.

## Pages

- `/registration/old-vehicle` (`OldVehicleJobsPage`, menu "งานรถเก่า"): summary tiles (รอทำ / รอตรวจรถ / รอยื่น / รอใบเสร็จ / รอป้าย-เล่ม / รอส่งงาน / ติดขัด, click to filter), dropdown filters (job type, status, customer, vehicle class, open / done / all) and a search box. Desktop = grid, one row per vehicle and one column per job group (งานโอน, ต่อภาษี, สลับเลข, คัดป้าย, ย้ายออก, ยกเลิกใช้), a status badge in the cell or `+` to receive that job; under 850px = list with status pills (user's choice). A badge opens the job dialog (choose / change type, link to the page of the next step via `nextStepHref`, ติดขัด, cancel intake); the vehicle opens its history and the edit form. The page reloads on window focus.
- `/registration/old-vehicle/inspection`, `/inspection/result`, `/inspection/passed` (`OldVehicleInspectionPage`): a queue separate from the new-registration inspection (user's choice). รอส่งตรวจ = tick vehicles, date, ส่งตรวจนอก / นำรถมาตรวจ, cost per vehicle, save, and print the sheet with `printInspectionSheet` (same format as new registration, no colour column data). รอผลตรวจ = ผ่าน / ไม่ผ่าน with a date. ตรวจผ่าน รอยื่น = link to the job's submit page.
- Page rule `/registration/old-vehicle` = ADMIN / STAFF_CAR / STAFF_MOTO / ACCOUNTANT (`PAGE_RULES`).

- Prices + เปลี่ยนเลขทะเบียน (built 2026-11-18, same day, after the user answered the open price questions): the prices are in `other-jobs.md` ("Prices of 2026-11-18") and the new job in `plate-swap.md` ("เปลี่ยนเลขทะเบียน"). In the hub a change-plate job is **not a ninth job type**: it is `jobType` `PLATE_SWAP` with `jobVariant` `CHANGE` (the real job is a `PlateSwap` row of kind `CHANGE`), so the grid column and the job-type option are labelled "สลับเลข / เปลี่ยนเลข" and the kind select has three choices (สลับเลข รถเก่า กับ รถใหม่ / รถเก่า กับ รถเก่า / เปลี่ยนเลขทะเบียน). `swapKind` accepts `CHANGE` at intake and in `PATCH jobs/:id/type`; no pair, no new vehicle. `nextStepHref` sends it to `/registration/plate-swap/{car,moto}/change/...`; the link interceptor also runs after `POST /api/plate-swaps/change`.

- Who keys intake (user 2026-11-18: "admin staff entry delivery"): `POST /api/old-vehicle-jobs/intake` is allowed only for ADMIN / STAFF_ENTRY / DELIVERY (`OldVehicleJobsService.isIntakeRole`, frontend `canIntakeOldJobs`). Those roles read and edit every vehicle class in the hub (vehicle data, job type, ติดขัด, cancel intake) but cannot record inspections. STAFF_CAR / STAFF_MOTO keep every later action for their own class (type, inspection, ติดขัด, cancel) and can no longer create an intake - Claude's literal reading of the answer, told to the user. `access-policy.ts`: own rules for `/api/old-vehicle-jobs` (read adds STAFF_ENTRY / DELIVERY), DELIVERY may now `GET /api/customers` and `GET /api/brands` (needed by the intake form); page rule `/registration/old-vehicle` and the sidebar's registration group include STAFF_ENTRY / DELIVERY. The new-vehicle picker is replaced by a note for accounts without STAFF_CAR / STAFF_MOTO (its search API belongs to the submit group). Not browser-tested with a STAFF_ENTRY / DELIVERY login.
- ติดขัด counts working days (user 2026-11-18): `blockedDays` and the overview alert use `workingDaysBetween` (Mon-Fri, public holidays unknown to the system), alert when more than 3 working days.
- Confirmed by the user 2026-11-18: late-transfer fine 200 applies to cars; move-in ลงขัน 100 is the Bangkok rate only. Billing of a change-plate job: see `billing.md` (job type `PLATE_CHANGE`).

  - Old menus hidden: `REGISTRATION_CATEGORIES` entries สลับเลข / งานโอน / ต่อภาษี / อื่นๆ carry `hidden: true`; the sidebar, `CreateCaseDialog` and `RegistrationOverview` list `MENU_CATEGORIES`.   - Pre-filled submit: the hub's "ยื่น" link is `<old submit page>?intake=<OldVehicleJob id>` (`nextStepHref`). `GET /api/old-vehicle-jobs/jobs/:id` returns `{ vehicle, job, pairVehicle }`; `useIntakePrefill` (`frontend/src/lib/use-intake-prefill.ts`, reads `window.location`, no Suspense) + `IntakeNotice` fill the eight submit forms: plate swap old/new (also the new vehicle picked at intake), old/old (both vehicles), change plate, transfer (all three types; ผู้โอน = owner at intake), move out, use cancel, plate copy, tax renewal (as manual entry with วันจดทะเบียนครั้งแรก / วันครบกำหนดภาษี). Everything stays editable; a job that was already filed is not filled.
  - Intake is mandatory: `OldVehicleJobsService.assertIntakeBeforeSubmit(path, body)` runs in `OldVehicleJobLinkInterceptor` before the create handler of plate swaps (`/`, `/pair`, `/change`), transfers, tax renewals, use cancellations, move outs and plate copies. 400 unless an open, unfiled intake exists for that chassis (`chassisKey`) with the same job type (transfer: the exact type; plate swap: the same variant) - and, when that intake needs an inspection, it must be PASS. Tax renewal of a vehicle picked from the new-registration database is checked by that vehicle's chassis. Jobs created before this rule are unaffected (they are already linked / backfilled). There is no ADMIN bypass.
