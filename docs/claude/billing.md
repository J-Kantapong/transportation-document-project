# Billing: collection accounts, rates, custom invoices, other jobs, invoice layout

Project documentation for Claude Code and Codex. Moved here unchanged from `CLAUDE.md` on 2026-11-16 to keep that file short; `CLAUDE.md` holds the index. Update this file when the feature changes.

- Collection accounts (user 2026-09-26/27): money goes into the company account (VAT) or a personal account (e.g. SPI,
  YMAC; no VAT). One account per customer, but it can move later (the user splits accounts to spread the tax base), so
  `CustomerAccountPeriod` keeps the history with a start date: a job belongs to the account in effect on its date
  (`accountOn` in `backend/src/billing/billing-account.ts`; no rows = company). Set on the billing page ("บัญชีรับเงิน",
  `GET/POST /api/billing/customers/:id/account` `{ account, effectiveFrom, remark }`, remark mandatory, AuditLog
  `set-account`). The billing queue returns `account` per customer and per vehicle (by delivered date). `Invoice.account`
  = the account of its vehicles (one bill may not mix accounts). Personal-account bills never have VAT (WHT still per
  customer), number in their own series (`suggestedPersonalInvoiceNo`), and print the personal issuer (name as on the
  bank account, no tax ID, no address yet) with its bank account: `PERSONAL_PROFILE` in `frontend/src/lib/company-profile.ts`.
  Per-customer payee (user 2026-10-08: SPI is paid into a different person's account, YMAC stays on the default one;
  migration `20261008130000_customer_personal_payee`): `Customer.personalPayeeName/Bank/AccountNo` (all null = the
  `PERSONAL_PROFILE` default). Set in the "บัญชีรับเงิน" editor on the billing page (`PUT /api/billing/customers/:id/personal-payee`
  `{ name, bank, accountNo, remark }`, name + account number together or all empty, AuditLog `set-personal-payee`; `GET .../account`
  returns `payee`). Invoices and quotations of a PERSONAL account copy it into `customerSnapshot.payee` at issue
  (`payeeSnapshot` in `billing.service.ts`), so reprints never change; `personalIssuerOf(payee)` builds the printed name + payment lines.
  The bank account number itself is data entered in the UI, never committed.
  `ServiceFeeRate.includesReceipt` (user 2026-09-27, YMAC): the price already includes the DLT receipt, so the service
  fee = price − that vehicle's actual receipt (`serviceFeeFromRate`; the billing page recalculates when the receipt is
  edited). YMAC prices (all-in): new motorcycle 650 (receipt 340), 300cc 1,200 (not used yet), tax renewal 150 (100),
  transfer 800 (105/130), transfer with fine 1,000 (305/330) - transfer and tax renewal are not billable in the system yet.
  Auto price matching (user 2026-09-28, "fewest mistakes"): `ServiceFeeRate.kind` = `BASE` (one per vehicle, chosen by
  vehicle kind/CC) or an add-on `OTHER_PROVINCE` (ขอใช้) / `URGENT`, added automatically when the vehicle is registered in
  another province than the owner's / its latest submission was urgent (`suggestAddOns`; queue rows carry `urgent`, `otherProvince`, `suggestedRateId`,
  `suggestedAddOnIds`). The billing page shows a rate dropdown + add-on checkboxes per vehicle and computes the fee
  (typing a fee only via "กำหนดเอง"), flags rows changed from the system's choice or with no matching rate, and shows a
  per-price breakdown before issuing. "ขอใช้" here = ขอใช้จังหวัดอื่น (registrationProvince ≠ ownerProvince, the same rule
  as the ธรรมเนียมอื่นๆ 20 fee), kind `OTHER_PROVINCE` - not a plate-number request; it will apply to cars too.
  `ServiceFeeRate.chassisPrefix` (user 2026-09-28, MC Superbike: chassis starting ML = 885, JH = 2685, both fall in the
  same 300-799cc bracket so CC alone can't tell them apart) - an optional prefix a BASE row's vehicle must match
  (case-insensitive `chassis.startsWith`), checked in `suggestRate` alongside vehicleKind/CC; null = unrestricted, same
  as before. Rate editor has an "เลขตัวถังขึ้นต้น" column.
  Rate filters by province / vehicle type (user 2026-10-09, บางบ่ออารียนต์: จดสมุทรปราการ 935 and ป้ายเหลือง รย.17 1,400 next to
  the normal 440, migration `20261009100000_service_fee_rate_province`): `ServiceFeeRate.registrationProvince` (full province
  name, validated against `PROVINCES`) and `ServiceFeeRate.bodyPrefix` (`Vehicle.body` prefix such as `รย.17-`), both nullable =
  unrestricted. `suggestRate` matches them against the vehicle's `registrationProvince` / `body` and tries the more specific rows
  first (province > body prefix > `sortOrder`), so a Samut Prakan row wins over the general row wherever it sits in the table;
  a vehicle without a province never matches a province row. The rate editor has "จังหวัดที่จด" and "ประเภทรถ" selects.
  Quotation `RATE` lines do not carry these fields (applied rates get null).
  Rate kind `PLATE_REQUEST` (user 2026-09-28, Spac EV: "ขอใช้เลข" priced separately from "ขอใช้" the province) = the
  vehicle's latest submission requested a plate number (`requestsPlateNumber`) - distinct from the pre-existing
  "ลูกค้าชำระค่าขอใช้เลขเอง" deduction checkbox on the billing row, which subtracts from an already-computed fee rather
  than suggesting one.
  Rate kind `TRANSFER_NOTICE` (user 2026-09-28, Spac EV: "แจ้งย้าย" 182.24, only for vehicles that actually go through
  แจ้งย้าย, not every vehicle) = `registrationProvince !== 'กรุงเทพมหานคร'` (`transferNotice` in `billing.service.ts`,
  same rule as `getTransferStatus` in `vehicles.service.ts`) - a different comparison from `OTHER_PROVINCE`
  (`registrationProvince !== ownerProvince`); the two are independent and can both apply to the same vehicle.
  Tick-only billing (user 2026-09-28): the queue is a compact list per delivery date (plate, chassis, "ใบเสร็จ x +
  ค่าบริการ y", tags), no sideways scrolling; details (receipt, rate, add-ons, bill text, ปิดงาน) sit behind "แก้"; cars
  with a problem (no receipt amount / no price) are flagged and cannot be ticked; a sticky bottom bar shows count + total
  and "ออกบิล" opens a confirm dialog (invoice no., date, job label, breakdown, extras, totals, preview). Receipt check
  (user 2026-09-28): queue rows carry `receiptEstimate` (Bill fees + tax computed at submission from the vehicle data); a
  receipt amount that differs is a blocking "ต้องตรวจ" with a hint (+ = maybe ขอใช้ though the data says no, − = the
  reverse) until the accountant ticks "ตรวจกับใบเสร็จจริงแล้ว" in "แก้" (found 2 real TWE cars with the wrong province).
  `receiptEstimate` is recomputed from the vehicle's current data + the submission's options (`currentBillEstimate`), so
  fixing the province clears the warning; "แก้" also shows the receipt photo(s) and an "แก้ข้อมูลรถ" link (ADMIN /
  STAFF_ENTRY) to `/registration/new-vehicle/entry?focus=<chassis>&edit=1&returnTo=/accounting/billing` (same tab),
  which opens that car's edit form and, after a successful save, returns to billing (`returnTo` only accepts the billing
  page); the ticked cars and the open "แก้" panel are restored from sessionStorage (`billing-return-v1`). "ใช้ตามใบเสร็จ" (user 2026-10-09: "ใบเสร็จถูกเสมอ", but a click is still required because the amount in the system is AI-read / typed): queue rows also carry `receiptEstimateFlipped` = the same estimate with ขอใช้ the other way round (`flipOtherProvince` swaps only `ownerProvince` in memory; null when it cannot be computed). When the receipt equals it exactly, "แก้" shows which way the receipt says and a button that ticks / unticks every `OTHER_PROVINCE` add-on of that vehicle kind and sets "ตรวจกับใบเสร็จจริงแล้ว"; it affects that bill's service fee only and never changes the vehicle's provinces (user's choice). Hidden for a "กำหนดเอง" price. The same check runs earlier: step 5 (รับใบเสร็จ) explains a "ไม่ตรง Bill"
  (maybe ขอใช้), links to the vehicle edit and asks for confirmation before saving; step 4 settings tag ขอใช้ cars. Company-account prices are always on top of the receipt (user); TWE: <300cc 520,
  300-799cc 885, ขอใช้ +100, ด่วน +100 (taken as before VAT).

- Separate inspection fee on the bill (user 2026-10-07 / 2026-10-14, SPI pays an outside-inspection fee of 1,000 or more itself, so it is a pass-through, not our cost): `GET /api/billing/queue` vehicles carry `inspectionSeparate` (`Vehicle.inspectionSentCost` when >= `INSPECTION_SEPARATE_FROM` = 1,000 in `billing.service.ts`, else null; applies to every customer, the rule was only stated for SPI). The issue dialog of `/accounting/billing` shows a notice for ticked vehicles with it and a button that adds one FEE line per vehicle ("ค่าตรวจสภาพรถ <plate or chassis>", no VAT, no WHT) to the bill items; it never adds anything silently and the lines stay editable or removable. No migration; not browser-tested (no dev login). Money cost of such inspections is left out of the profit analysis file for SPI (G:My DriveTradeinterClaudeวิเคราะห์ราคา).

- Custom invoices and per-bill WHT (user 2026-09-29): `/accounting/billing/custom` issues a bill with free-typed lines and
  no vehicles (old jobs moved from the previous system, goods sales such as selling a company car). `InvoiceItem` (kind,
  description, quantity, unitPrice, amount = quantity x unitPrice computed by the server, cost per unit, sortOrder) with
  kinds `FEE` (no VAT, no WHT), `SERVICE` (VAT + WHT), `GOODS` (VAT, no WHT); `Invoice.goodsTotal` holds the goods sum,
  VAT = (service + goods) x rate, WHT = service x rate. `cost` is internal (never printed, null = unknown, always null
  for FEE); profit = (unitPrice - cost) x quantity per line. The same lines can also go on a vehicle bill (`items` on
  `POST /api/billing/invoices`; the billing page's confirm dialog and the edit dialog use the shared
  `components/InvoiceItemsEditor.tsx`, which replaced the old "ค่าใช้จ่ายอื่นๆ" box for new bills; old bills keep their
  `extras`). On a mixed bill the vehicle fee line and the attachment total count vehicles only, and the attachment notes
  the other lines. API: `POST /api/billing/custom-invoices` { customerId, invoiceNo, issueDate, jobLabel, items, whtRate? }, `GET
  /api/billing/next-invoice-no`, `GET /api/billing/invoices/:id`; `PATCH /api/billing/invoices/:id` also takes `items`
  (full replace) and `whtRate`. The bill's account = the customer's account on the issue date; numbering shares the
  vehicle bills' series. A bill without vehicles prints one page (no attachment); "แก้ไขบิล" on such a bill opens the
  custom page with `?edit=<id>`. Every bill (vehicle, custom, and edits) can override the WHT rate
  (`components/WhtRatePicker.tsx`: ตามลูกค้า / 1% / 3% / ไม่หัก / อัตราอื่น); a rate different from the customer's
  (or, when editing, the bill's own) must be ticked as checked before saving. Invoices print "ค่าบริการ" instead of
  "ค่าดำเนินการ" (reprints of old bills too).

- Other jobs in billing (user 2026-10-07 "ดึงงานทุกประเภทมาในการวางบิล", migration `20261007100000_other_jobs_billing`, code `backend/src/billing/other-jobs.ts` + `BillingService.otherJobsQueue/createJobInvoice`, page `/accounting/billing/jobs`, ADMIN + ACCOUNTANT): งานโอน, ยกเลิกการใช้รถ, คัดแผ่นป้าย, ย้ายออก (billable once `returnedDate` is set = receipt back, and since 2026-10-08 also `deliveredDate` = handed to the customer on a DL slip, see "Delivery of other jobs" below) and ต่อภาษี (once `deliveredDate` and `paymentDate` are set) with an owner (`customerId`) and not cancelled wait in a queue per customer; plate swap stays on the vehicle bill and Yamaha stays on the quotation / custom bill. Each picked job becomes a `FEE` line (the real receipt amount, else the computed Bill and flagged "ยังไม่มียอดใบเสร็จ"; ต่อภาษี = its `billTotal`) plus a `SERVICE` line (price per customer, cost = No Bill + ค่าอากร), both carrying `InvoiceItem.sourceType/sourceId`. ค่าอากร is not billed as its own line (Claude's choice, not confirmed). Service prices live in `JobFeeRate` (customer + jobType + vehicleClass CAR|MOTO|ANY + optional transfer variant OWNER|INSPECTION, first row by `sortOrder` wins, separate from `ServiceFeeRate`); no matching row = the accountant must type the price (blank blocks issuing, 0 is allowed). `JobFeeRate.includesReceipt` (user 2026-10-13, YMAC all-in prices, migration `20261013120000_job_fee_rate_includes_receipt`, additive): the price already includes the government fee, so the suggested service fee = price − that job's fee (`suggestedJobServiceFee` = `serviceFeeFromRate`, e.g. transfer 800 − 105 = 695); a fee above the price suggests nothing and warns. Ticked as "รวมใบเสร็จ" in the rate editor; `PUT .../job-rates` rows take `includesReceipt`. Browser-checked 2026-10-13 on the dev database (rate editor shows the checkbox, queue endpoint answers 200 so the column exists there); saving a rate and the suggested fee were only unit-tested. API: `GET /api/billing/other-jobs` -> { suggested numbers, customers[{ terms, rates, jobs[{ fee, feeSource, suggestedServiceFee, warnings }] }] }, `POST /api/billing/other-jobs/invoice` { customerId, invoiceNo, issueDate, jobLabel?, whtRate?, jobs[{ type, id, serviceFee, serviceLabel }] } (the server recomputes fees, locks the job rows, refuses a job already in a non-VOID invoice; customers needing a quotation are blocked), `GET/PUT /api/billing/customers/:id/job-rates` (PUT needs `remark`, AuditLog entity `Customer` action `job-rates`). A voided bill frees its jobs. Editing such a bill (`PATCH /api/billing/invoices/:id`) keeps the linked lines (read-only in the editor, `items` replaces only the typed lines); to fix a job's price or remove it, void the bill and issue again. The same jobs can be put on a vehicle bill (user 2026-10-07): `POST /api/billing/invoices` takes `jobs` (same shape; the server locks Vehicle rows first, then the job tables, and refuses when the customer's account at the issue date differs from the vehicles' account), and the confirm dialog of `/accounting/billing` lists the customer's waiting jobs with a tick + price box. One billing page (user 2026-11-11 "อยากจะวางบิลร่วมกัน", no migration): `/accounting/billing` now lists, per customer, the new vehicles **and** a "งานอื่นๆ ส่งงานแล้ว รอวางบิล" table (tick + service price per job, select-all; typing a price ticks the job) on the main page; the confirm dialog only summarises the ticked jobs. Customers with only other jobs are in the customer chips too (`billingCustomers` = billing queue + other-jobs queue; such a customer has no vehicle rates loaded, so the rate editor is replaced by a link to `/accounting/billing/customers`). `POST /api/billing/invoices` accepts `lines: []` when `jobs` is not empty (account = the customer's account on the issue date, like `createJobInvoice`; neither = 400 'ต้องเลือกรถหรืองานอย่างน้อย 1 รายการ'), so a jobs-only bill can carry typed lines too. `/accounting/billing/jobs` stays for job prices, closing jobs and the old flow. Browser-checked against a throwaway fixture API (mixed bill and jobs-only bill: totals, dialog, preview, request body); not tested against the real backend. Each linked line also stores `InvoiceItem.sourceSnapshot` (chassis, plate, brand, owner, receipt no., done date, class, variant) so the attachment prints from the bill alone. Browser-tested on dev 2026-10-07 with test rows (removed afterwards). Close - billed outside (user 2026-10-13, migration `20261013140000_job_billing_closure`, additive): `JobBillingClosure` (jobType + jobId unique, note, closedAt, closedById; no FK to the job, like `InvoiceItem.sourceType/sourceId`) takes a delivered job out of the queue and refuses it in `createJobInvoice` / vehicle bills (`closedNote` on `loadJobs`). `POST /api/billing/other-jobs/close` { type, id, note } (ADMIN + ACCOUNTANT, note mandatory), `POST .../reopen` { type, id, remark } (ADMIN only, rule in `access-policy.ts`), `GET .../closed?offset` -> { jobs, hasMore }; every close / reopen goes to AuditLog entity of the job (`VehicleTransfer`, `PlateCopy`, ...; actions `billing-close` / `billing-reopen`). UI: "ปิดงาน" per row on `/accounting/billing/jobs` and the "ปิดงานแล้ว" panel with เปิดงานกลับ (`components/OtherJobClosing.tsx`). Browser-tested on dev 2026-10-13 (close, empty-note refusal, billing and re-closing refused, reopen, AuditLog rows shown on the activity page as ปิดงาน - วางบิลนอกระบบ / เปิดงานกลับ with a link to the jobs billing page; the test job was reopened afterwards). Not built: editing a linked line's price in an issued bill, the executive overview's money tied up for these jobs.

- Invoice face layout (user 2026-10-07 "รวมเป็นค่าธรรมเนียมรวม แล้วก็ค่าบริการรวม", same migration): `Invoice.faceLayout` = `SUMMARY` for every bill issued from then on (DB default) and `GROUPED` for older rows (set by the migration so reprints look like what the customer received). `invoiceFaceLines` in `frontend/src/lib/invoice.ts`: SUMMARY = one "ค่าธรรมเนียมราชการ (จดทะเบียนรถยนต์ 4 คัน, งานโอน 3 งาน) ตามเอกสารแนบเลขที่ IV…-A" line + one "ค่าบริการ (…)" line, then the typed lines (งานเก่า / ขายสินค้า) and old `extras` as their own lines; GROUPED = the old per-price grouping. A bill with no vehicles and no linked jobs (custom bill) has no attachment and prints its lines directly in both layouts. The attachment (`attachmentPagesHtml` in `invoice-print.ts`) is now one table per content type: the vehicle table (unchanged columns) then one table per job type (brand, chassis, plate, receipt no. / for ต่อภาษี the delivered date, ค่าธรรมเนียม or ภาษีที่ชำระ, ค่าบริการ, VAT, รวม), numbered titles only when there is more than one table, a "รวมทุกตาราง" row, paged 40 units per page with the table header repeated on a continued page. The tax invoice reuses the bill's layout (`TaxInvoice.faceLayout`, items carry `sourceType`), and refers to the attachment whenever the bill has vehicles or jobs.
